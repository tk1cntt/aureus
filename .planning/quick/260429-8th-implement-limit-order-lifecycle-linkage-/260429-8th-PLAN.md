<interfaces>
Research recommendation from quick 260429-897 is locked for this plan:
- Separate `pending_order_id`, `deal_ticket`, `position_ticket`.
- Emit/use `ORDER_PENDING_PLACED` when MT5 accepts a pending LIMIT/STOP order.
- Emit/use `ORDER_FILLED` when a real `DEAL_ENTRY_IN` fill creates a deal/position.
- Only set journal `status='EXECUTED'` on real fill, never on pending placed.
- Forward `trace_id` and `cmd_id` as durable correlation keys; comment suffix is fallback only.
- DB E2E is mandatory because persistence/schema path changes.

Current known contracts:
- `build_order_command(match_event)` currently returns MT5 command fields and intentionally omits bulky scoring/snapshot payloads.
- `OrderDispatcher._extract_mt5_execution_payload(order)` allowlists fields before publishing to MT5.
- `OrderDispatcher.dispatch_order()` currently treats immediate `ORDER_OPENED` as final execution and then calls `journal.on_strategy_match()` + `journal.on_order_opened()`.
- `OrderDispatcher.event_listener()` currently routes `ORDER_CLOSED`/`ORDER_CLOSED_PARTIAL` to `journal.on_order_closed()` and resolves pending futures by `cmd_id`.
- `TradeJournalManager.on_order_opened(event)` currently requires `trace_id`, `ticket`, positive entry price, MT5 time, then updates `status='EXECUTED' WHERE trace_id=$8 AND status='TRIGGERED'`.
- `AureusProvider.mq5::ExecuteOpenOrder()` currently sends `TRADE_ACTION_PENDING` for LIMIT/STOP but still pushes `ORDER_OPENED` with `result.order` for non-market branches.
- `AureusProvider.mq5::OnTradeTransaction()` currently handles `DEAL_ENTRY_OUT`; it must add `DEAL_ENTRY_IN` handling for fill events.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Redis MT5 events -> trader dispatcher | Untrusted/externally produced event payload crosses into Python persistence path. |
| Trader journal -> PostgreSQL | Event fields become SQL parameters and lifecycle state transitions. |
| Strategy event -> MT5 command | Strategy payload fields are forwarded to MQL5 provider. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-260429-8TH-01 | Spoofing | `dispatcher.event_listener()` | mitigate | Require stable correlation (`trace_id`, `cmd_id`, or `pending_order_id`) before journal updates; ignore fill/pending events that cannot be linked to an existing journal record. |
| T-260429-8TH-02 | Tampering | `journal.py` SQL update path | mitigate | Use parameterized SQL only; validate positive prices/tickets and MT5 time before status transition. |
| T-260429-8TH-03 | Repudiation | lifecycle persistence | mitigate | Persist `pending_order_id`, `entry_deal_ticket`, `cmd_id`, and `mt5_comment` so audit can distinguish placement from fill. |
| T-260429-8TH-04 | Denial of Service | malformed MT5 events | mitigate | Event handlers return false/log warnings on invalid payloads without blocking Redis listener; async journal tasks keep close/fill routing non-blocking. |
