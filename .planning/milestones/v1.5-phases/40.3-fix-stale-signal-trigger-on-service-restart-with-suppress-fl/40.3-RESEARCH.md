# Phase 40.3: Fix Stale Signal Trigger on Service Restart — Research

**Researched:** 2026-04-13
**Domain:** Python asyncio — Aureus Signal Engine startup flow, Redis state management, Redis Stream consumer
**Confidence:** HIGH

## Summary

The aureus-signal service fires false-positive signals and strategy triggers on restart because three distinct code paths emit data from stale/historical candles during the startup warmup phase, before any real-time gateway candles arrive. All three paths are in `live_engine.py` and can be guarded by a single suppress flag on `SymbolState`.

The evidence confirms the root cause analysis in `.planning/intel/startup-signal-trigger-analysis.md`. The code has been read in full, and exact insertion points have been verified with current line numbers.

**Primary recommendation:** Add `_signal_suppressed = True` on SymbolState after snapshot restore. Suppress `publish_signal_event` and `evaluate_all` calls while flag is True. Reset flag on first gateway candle. Clear `transient_signals` after delta loop as defensive cleanup.

### Anti-Patterns to Avoid

- **Do NOT modify `state.py` to add `_signal_suppressed` to `to_dict()`** — the flag must be ephemeral. Using `setattr` directly on the instance ensures it won't serialize.
- **Do NOT suppress signal calculation** — delta candles need to run signal calculators to build state (OB zones, FVG detection, EMA convergence). Only suppress emission/publish.
- **Do NOT check backfill_status as suppression mechanism** — it already exists (`window_manager.set_backfill_status`) but is used for UI/dashboard purposes, not signal gating. The suppress flag is a separate, explicit guard.

## Common Pitfalls

### Pitfall 1: Suppress flag set only in snapshot-restore path, not no-snapshot path
**What goes wrong:** If no snapshot exists (line 405+ "no snapshot found" path), the code still processes 1500 warmup candles and may emit signals. If `_signal_suppressed` is only set in the snapshot path, the no-snapshot path is unprotected.
**Why it happens:** The flag insertion point (after line 369) is only inside the `if latest_snap_row:` branch.
**How to avoid:** Also set `_signal_suppressed = True` in the no-snapshot path (after line 405), OR better: set it unconditionally at the start of the warmup block for all symbols, before the if/else.
**Warning signs:** On first-ever service start (no snapshots yet), false signals could still fire.

### Pitfall 2: Flag reset triggers on stale gateway replay
**What goes wrong:** If the gateway has buffered/replayed messages from before the crash, the first "new" candle might actually be an old candle with timestamp < snapshot time.
**Why it happens:** Redis Stream consumer groups track position, but after a crash the consumer group was recreated (line 278 `xgroup_create(..., id="0")`), which starts from the beginning of the stream. However, pending entries are purged (lines 284-297), so only NEW messages after service start will arrive.
**How to avoid:** The CONTEXT.md decision to check `candle timestamp > last_snapshot_time` is correct. However, with pending purge, the `">"` in `streams_subscription` (line 608) ensures only NEW candles are read, not old ones. This is already protected by the consumer group design.
**Risk level:** LOW — the pending purge + `">"` subscription provides sufficient protection.

### Pitfall 3: `integrity_and_recalc_task` fires during suppressed period
**What goes wrong:** The background task at line 487 waits 60 seconds (line 1158), then calls `recalculate_all_signals` which calls `evaluate_all` at line 1119. This could fire strategies before the first gateway candle arrives.
**Why it happens:** `recalculate_all_signals` has its own `evaluate_all` call (line 1119) that does NOT check `_signal_suppressed`.
**How to avoid:** CONTEXT.md explicitly defers this ("Recalculation path suppression — handle later if needed"). The 60-second initial delay + 180-second gap check interval means it's unlikely to fire before the first gateway candle. However, this IS a potential gap.
**Recommendation:** If the first gateway candle arrives within 60 seconds (typical for active markets), the suppress flag will already be cleared by then. For safety, the planner should note this as a known edge case and monitor.

### Pitfall 4: `_signal_suppressed` leaked into Redis serialization
**What goes wrong:** If `to_dict()` accidentally includes `_signal_suppressed`, the flag would persist across restarts.
**Why it happens:** `to_dict()` iterates over `self.__dict__` or lists attributes manually.
**How to avoid:** `to_dict()` in `state.py` (lines 438-487) manually constructs the return dict — it does NOT iterate over `__dict__`. Any attribute not explicitly listed will NOT be serialized. Since `_signal_suppressed` is set via `setattr` and not listed in `to_dict()`, it is safe.
**VERIFIED:** `to_dict()` manually constructs the dict with explicit keys only. `_signal_suppressed` will NOT be serialized. [VERIFIED: state.py lines 438-487]

### Pitfall 5: Multi-symbol concurrency
**What goes wrong:** The suppress flag is per-symbol (on SymbolState), but the gateway loop processes multiple symbols. If one symbol gets its first candle before another, only that symbol's flag resets.
**How to avoid:** This is actually correct behavior — each symbol should independently transition from suppressed to active. No pitfall here.
