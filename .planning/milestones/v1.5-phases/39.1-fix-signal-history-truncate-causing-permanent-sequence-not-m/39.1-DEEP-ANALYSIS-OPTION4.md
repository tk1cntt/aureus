## 1. Option 3 (Hybrid) - Phân tích chi tiết

### 1.1 Cơ chế đề xuất

Option 3 kết hợp 2 lớp bảo vệ:

**Lớp 1: Reactive (Clear khi tất cả events bị skip)**
```python
if triggered_t > 0 and current_step_index == 0:

    if len(source_records) > 0 and newer_events == 0:

```

**Lớp 2: Proactive (Timeout safety)**
```python
candles_since_trigger = internal_candle_counter - trigger_candle_counter

    triggered_t = 0  # Clear sau N candles
```

### 1.2 ✅ Điểm tốt

| Aspect | Why it works |
|--------|-------------|
| **Reactive layer** | Chỉ clear khi THỰC SỰ bị block, không clear bừa |
| **Timeout layer** | Safety net nếu reactive layer miss edge case |
| **Additive change** | Không sửa logic hiện tại, chỉ THÊM check mới |
| **Low risk** | Nếu clear sai, strategy vẫn reject normally (không double-trigger) |

#### GAP #1: Race Condition giữa Trigger và Clear

**Scenario:**

```
T0: Strategy trigger tại bar_t=1000
    → evaluate() gọi _reset_sequence_state(triggered_t=1000)
    → executor_strategy_progress[symbol][strategy] = {triggered_t: 1000, ...}

T1: Nến mới đến (ts=1060)
    → executor_state.strategy_progress = executor_strategy_progress[symbol]
    → _evaluate_sequence() chạy
    → Reactive layer check: newer_events = 0 → triggered_t = 0 ✅
    → BUT: triggered_t chỉ bị clear TRONG LOCAL VARIABLE
    → Cuối _evaluate_sequence(), progress_data được lưu lại:
       state_obj.strategy_progress[self.name] = progress_data
       → progress_data["triggered_t"] = 0 ✅ (OK cho lần này)

T2: Nến tiếp theo (ts=1120)
    → executor_state.strategy_progress = executor_strategy_progress[symbol]
    → WAIT! executor_strategy_progress[symbol] có được update không?
```

**VẤN ĐỀ:** 

```python
# strategy_executor.py line 381
executor_state.strategy_progress = executor_strategy_progress.get(symbol, {})
```

Đây là **reference assignment**, không phải copy. Khi `_evaluate_sequence` sửa:
```python
state_obj.strategy_progress[self.name] = progress_data
```

Thì `executor_strategy_progress[symbol][strategy_name]` CŨNG được update theo → **OK, không có race condition**.

**KẾT LUẬN:** GAP này **KHÔNG TỒN TẠI** vì Python dùng reference. ✅

#### GAP #2: last_processed_record_index KHÔNG được reset sau khi clear triggered_t

**Scenario:**

```python
# Sau khi clear triggered_t (reactive layer)
triggered_t = 0  # Clear xong

# NHƯNG last_processed_record_index vẫn giữ nguyên
# Ví dụ: last_processed_record_index = 106 (đã xử lý đến record 106)

# Lần evaluate tiếp theo:
pending_records = []
for idx, rec in enumerate(source_records):
    if idx > last_processed_record_index:  # idx > 106
        pending_records.append((idx, rec))

# Nếu source_records chỉ có 107 records (index 0-106)
# → pending_records = [] → KHÔNG CÓ GÌ ĐƯỢC PROCESS!
```

**Root cause:**

Khi clear `triggered_t`, chúng ta cho rằng "sẽ process lại events cũ", nhưng:
- `last_processed_record_index` vẫn trỏ vào record cuối cùng
- Events cũ (index <= last_processed_record_index) sẽ BỎ QUA vì đã "processed"
- Chỉ events MỚI (index > last_processed_record_index) được process

**Impact:** 

Sau khi clear `triggered_t`, chúng ta CẦN process lại events cũ, nhưng cơ chế index tracking ngăn điều này!

**Fix cần thiết:**

Khi clear `triggered_t`, cũng phải reset `last_processed_record_index`:

```python
if len(source_records) > 0 and newer_events == 0:
    triggered_t = 0
    last_processed_record_index = -1  # ← QUAN TRỌNG: Reset để reprocess events
    last_processed_t = 0
```

**NHƯNG WAIT!** Nếu reset `last_processed_record_index = -1`, chúng ta sẽ **reprocess TẤT CẢ** events cũ, bao gồm cả events đã matched trước đó. Điều này có thể gây:
- Duplicate matching (match lại signals đã match)
- Sequence confusion (match step 1 nhiều lần)

**Giải pháp đúng:**

Không reset `last_processed_record_index`, mà chỉ clear `triggered_t` để các events **MỚI** (chưa từng process) có t > triggered_t được process.

**BUT** vấn đề là: events cũ đã được process rồi, không cần process lại! Chỉ cần events MỚI (t > old triggered_t) được phép process.

**REAL FIX:**

Vấn đề KHÔNG PHẢI ở last_processed_record_index. Vấn đề là:

```python
# Line 237-241
if triggered_t > 0 and latest_time <= triggered_t:
    continue  # Skip
```

Khi clear `triggered_t = 0`, điều kiện này trở thành:
```python
if 0 > 0 and latest_time <= 0:  # FALSE → không skip
```

→ Events sẽ được process BÌNH THƯỜNG, kể cả events cũ.

**NHƯNG** events cũ đã được process rồi (idx <= last_processed_record_index), nên chúng KHÔNG nằm trong `pending_records`!

**REAL REAL ROOT CAUSE:**

Sau khi clear `triggered_t`:
- `pending_records` = các records có `idx > last_processed_record_index`
- Nếu không có records mới → `pending_records = []` → không có gì để process
- Strategy sẽ đợi records MỚI đến

**This is actually CORRECT behavior!** 

Vì:
1. Events cũ đã được process → không cần process lại
2. Chỉ cần events MỚI (t > old_triggered_t) được phép match
3. Khi clear `triggered_t = 0`, events mới sẽ KHÔNG bị skip bởi line 237

**KẾT LUẬN:** GAP này **KHÔNG CẦN FIX last_processed_record_index**. Chỉ cần clear `triggered_t` là đủ. ✅

#### GAP #3: Triggered_t có thể được set lại thành 0 quá sớm

**Scenario nguy hiểm:**

```
T0: Strategy trigger tại t=1000
    → triggered_t = 1000

T1: Nến tại t=1060 (60s sau)
    → Reactive layer check: newer_events = 0 → triggered_t = 0
    
T2: Nến tại t=1065 (5s sau, CÙNG nến với T1 nếu là M5)
    → Events từ t=1060 vẫn còn trong history
    → triggered_t = 0 → KHÔNG skip events cũ
    → Strategy match lại events từ t=1060
    → Strategy trigger LẦN NỮA tại t=1065! ❌ DOUBLE TRIGGER!
```

**Root cause:**

Reactive layer clear `triggered_t` QUÁ SỚM, trước khi market có time để tạo signals MỚI.

**Fix:**

KHÔNG nên clear `triggered_t` ngay lập tức. Thay vào đó:
- Đợi N candles (timeout layer)
- HOẶC đợi đến khi có events MỚI thực sự (t > triggered_t)

**Option 3 đã có timeout layer (10 candles)** → Đây là safety net tốt.

**NHƯNG** reactive layer (clear ngay khi newer_events == 0) là QUÁ NHANH.

**Improved Reactive Layer:**

```python
# Chỉ clear nếu ĐÃ WAIT đủ lâu
if triggered_t > 0 and current_step_index == 0:
    newer_events = sum(1 for rec in source_records if rec["t"] > triggered_t)
    
    # ĐỪNG clear ngay nếu có records mới đến (chưa đến lúc block hoàn toàn)
    # Chỉ clear khi THỰC SỰ không có events mới trong thời gian dài
    if newer_events == 0 and len(source_records) > 0:
        # Check if we've seen any new records since trigger
        newest_record_t = max(rec.get("t", 0) for rec in source_records if isinstance(rec, dict))
        if newest_record_t <= triggered_t:
            # KHÔNG có record MỚI NÀO từ khi trigger → có thể bị stall
            # BUT vẫn đợi timeout để an toàn
            pass  # Không clear ở đây, để timeout layer lo
```

**KẾT LUẬN:** Reactive layer trong Option 3 **QUÁ AGGRESSIVE**. Nên:
- **BỎ** reactive layer (hoặc làm nó conservative hơn)
- **DÙNG** timeout layer làm primary mechanism

#### GAP #4: Timeout layer dùng internal_candle_counter nhưng KHÔNG track trigger_candle_counter

**Current state:**

```python
# Line 136
internal_candle_counter = state.get("internal_candle_counter", 0)

# Timeout layer cần:
candles_since_trigger = internal_candle_counter - trigger_candle_counter
```

**Problem:** `trigger_candle_counter` KHÔNG được lưu khi trigger!

Trong `_reset_sequence_state` (line 444-471):
```python
state_obj.strategy_progress[self.name] = {
    ...
    "internal_candle_counter": internal_candle_counter,  # ← Có lưu
    "triggered_t": triggered_t,
    # NHƯNG KHÔNG CÓ trigger_candle_counter!
}
```

**Fix:**

Khi trigger, phải lưu `trigger_candle_counter`:

```python
# In evaluate() khi trigger (line 517-522)
self._reset_sequence_state(
    state_obj,
    triggered_t=bar_t,
    last_processed_t=progress_data.get("last_processed_t", 0),
    internal_candle_counter=progress_data.get("internal_candle_counter", 0),
)

# In _reset_sequence_state, add:
state_obj.strategy_progress[self.name] = {
    ...
    "internal_candle_counter": internal_candle_counter,
    "trigger_candle_counter": internal_candle_counter,  # ← THÊM DÒNG NÀY
    "triggered_t": triggered_t,
}
```

Hoặc đơn giản hơn: dùng luôn `internal_candle_counter` từ state (nó đã được persist):

```python
# When trigger happens at T0:
# internal_candle_counter = 5 (ví dụ)
# _reset_sequence_state saves: internal_candle_counter = 5

# At T1 (next candle):
# internal_candle_counter = 6 (incremented at line 149)
# candles_since_trigger = 6 - 5 = 1 ✅

# At T11:
# internal_candle_counter = 16
# candles_since_trigger = 16 - 5 = 11 > 10 → timeout fires ✅
```

**WAIT!** Line 149: `internal_candle_counter += 1`

Mỗi lần `_evaluate_sequence` được gọi, counter tăng 1. Vậy:
- Khi trigger: `internal_candle_counter = N`
- Lần eval tiếp theo: `internal_candle_counter = N+1`
- `candles_since_trigger = (N+1) - N = 1` ✅

**This works!** Không cần thêm field mới. ✅

#### GAP #5: Executor restart làm mất internal_candle_counter

**Scenario:**

```
T0: Strategy trigger → internal_candle_counter = 100
T1: Service restart (deploy, crash, etc.)
T2: Service start → executor_strategy_progress = {} (TRỐNG!)
T3: Signal đến → evaluate() chạy lần đầu
    → state.get("internal_candle_counter", 0) = 0 ← RESET VỀ 0!
    → candles_since_trigger = 0 - 0 = 0
    → Timeout KHÔNG fire (cần > 10)
```

**Root cause:**

Khi executor restart, `executor_strategy_progress` bị reset về `{}` (line 227-231):
```python
executor_strategy_progress = {}
for symbol in symbols_list:
    executor_strategy_progress[symbol] = {}  # ← TRỐNG!
```

Lần đầu `evaluate()` chạy:
```python
state = state_obj.strategy_progress.get(self.name, {})
internal_candle_counter = state.get("internal_candle_counter", 0)  # = 0
```

**BUT** đây thực ra là **correct behavior** vì:
- Sau restart, chúng ta muốn strategies bắt đầu lại từ đầu
- `triggered_t` cũng = 0 (do state reset)
- Không cần timeout vì triggered_t đã = 0

**KẾT LUẬN:** GAP này **KHÔNG TỒN TẠI** trong practice vì sau restart, triggered_t = 0. ✅

## 2. Các Gaps Kiến Trúc Sâu Hơn

### GAP #6: Signal History Truncation Vẫn Là Root Cause Cuối Cùng

**Observation:**

Tất cả các gap trên đều là **symptom** của vấn đề lớn hơn:

**Signal history bị truncate ở 500 records** (Phase 39.1 D-03).

Sau ~500 candles:
- Events cũ nhất bị pop
- Nếu `triggered_t` vẫn > 0, events còn lại đều có `t <= triggered_t`
- Stall xảy ra

**Real fix:**

Không nên dựa vào `triggered_t` để filter events. Thay vào đó:

**Option A: Dùng event ID thay vì timestamp**
```python
# Mỗi event có ID duy nhất
event_id = f"{record_idx}_{ev_tag}_{record_time}"

# Track đã process event nào
processed_event_ids = state.get("processed_event_ids", set())

if event_id not in processed_event_ids:
    process_event(...)
    processed_event_ids.add(event_id)
```

**Pros:** Không cần filter by time, không bị stall do truncation  
**Cons:** Memory overhead (phải track set của event IDs)

**Option B: Clear triggered_t khi sequence reset**
```python
# In _reset_sequence_state (khi strategy trigger)
def _reset_sequence_state(self, state_obj, triggered_t=0, ...):
    state_obj.strategy_progress[self.name] = {
        ...
        "triggered_t": triggered_t,
    }
    
    # NEW: Clear triggered_t sau N candles
    state_obj.strategy_progress[self.name]["_trigger_timeout_at"] = \
        state.get("internal_candle_counter", 0) + 10  # Timeout sau 10 candles
```

```python
# In _evaluate_sequence
trigger_timeout_at = state.get("_trigger_timeout_at", 0)
if trigger_timeout_at > 0 and internal_candle_counter >= trigger_timeout_at:
    triggered_t = 0
    trigger_timeout_at = 0
```

**Pros:** Explicit timeout, dễ debug  
**Cons:** Thêm 1 field mới vào state

## 3. Phương Án Tối Ưu: Option 4 (Better Hybrid)

### 3.1 Design Principles

1. **Đơn giản nhất có thể** — ít code = ít bug
2. **Explicit timeout** — dễ debug, dễ config
3. **Không sửa logic hiện tại** — chỉ THÊM code mới
4. **An toàn > Nhanh** — thà đợi lâu hơn 1 nến còn hơn double-trigger

### 3.2 Implementation

**Chỉ dùng Timeout Layer** (bỏ Reactive Layer):

```python
# Chèn vào _evaluate_sequence, SAU line 149 (internal_candle_counter += 1)

# --- Phase 39.1 Fix: Clear triggered_t after timeout to prevent post-trigger stall ---
if triggered_t > 0 and current_step_index == 0:
    trigger_counter = state.get("_trigger_candle_counter", 0)
    candles_since_trigger = internal_candle_counter - trigger_counter
    TRIGGER_TIMEOUT = 10  # Candles to wait before clearing triggered_t
    
    if candles_since_trigger > TRIGGER_TIMEOUT:
        logger.info(
            f"[{symbol}] [{self.name}] [trigger_timeout] "
            f"Clearing triggered_t={triggered_t} after {candles_since_trigger} candles "
            f"to prevent post-trigger stall"
        )
        triggered_t = 0
```

**Và khi trigger, phải lưu `_trigger_candle_counter`:**

```python
# In _reset_sequence_state (line 444-471)
state_obj.strategy_progress[self.name] = {
    ...
    "triggered_t": triggered_t,
    "_trigger_candle_counter": internal_candle_counter,  # ← ADD THIS
}
```

**Và trong evaluate() khi trigger (line 517-522):**

```python
self._reset_sequence_state(
    state_obj,
    triggered_t=bar_t,
    last_processed_t=progress_data.get("last_processed_t", 0),
    internal_candle_counter=progress_data.get("internal_candle_counter", 0),
)
# ← _reset_sequence_state sẽ tự lưu _trigger_candle_counter
```

### 3.3 Tại sao Option 4 tốt hơn Option 3?

| Aspect | Option 3 (Hybrid) | Option 4 (Timeout Only) |
|--------|------------------|------------------------|
| **Complexity** | 2 layers, nhiều code hơn | 1 layer, ít code |
| **Race conditions** | Reactive layer có thể clear quá sớm | Không có |
| **Debug** | Khó biết layer nào fire | Dễ: chỉ check candle count |
| **Config** | 2 params (timeout + threshold) | 1 param (timeout) |
| **Safety** | Reactive có thể double-trigger | Chỉ timeout sau N candles |
| **Lines of code** | ~40 lines | ~15 lines |

### 3.4 Timeout Value: Tại sao 10 candles?

| Timeframe | 10 candles = | Rationale |
|-----------|-------------|-----------|
| M1 | 10 phút | Đủ time để market tạo signals mới |
| M5 | 50 phút | OK cho swing trading |
| M15 | 2.5 giờ | reasonable |
| H1 | 10 giờ | OK |
| H4 | 40 giờ (~1.5 ngày) | Hơi lâu nhưng an toàn |

**Configurable sau:** Có thể đưa vào `trade_execution.trigger_timeout_candles`
